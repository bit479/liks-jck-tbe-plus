# 高清渲染问题审查报告

## 1. 审查范围与方法

- 仓库：`https://github.com/bit479/liks-jck-tbe-plus.git`
- 本地目录：`liks-jck-tbe-plus/`
- 审查对象：`tbeplus/ui.py`、`theme.py`、`widgets.py`、`motion.py`、`ui_classic.py`，以及 `engine.py`、`client.py`、`newsapi.py`、`config.py` 的依赖关系。
- 方法：逐行阅读实际代码 + 现有截图（`docs/screenshots/`）+ 本轮 Tkinter 深色改造后的渲染截图（`docs/ui-redesign/_preview/tk-*.png`）；未修改业务文件。

## 2. 结论摘要

当前界面**所有视觉元素都由 Tkinter Canvas 手工绘制**。Tk 8.6 的 Canvas 不提供抗锯齿（Anti-Aliasing），这是圆角、按钮、边框边缘发毛的**架构性原因**，无法通过继续加密折线彻底解决。DPI 方面仅做了 `PROCESS_SYSTEM_DPI_AWARE`（系统级），未做 Per-Monitor V2，也没有处理 `WM_DPICHANGED`；跨不同缩放比例的显示器会出现位图拉伸与尺寸不一致。图标使用 Segoe MDL2 字体码位 + 固定尺寸 PNG，没有矢量图标体系。要同时满足“抗锯齿、高 DPI、矢量图标”，需要引入具备 QPainter/QPainterPath 与完整高 DPI 模型的框架（Qt）。

## 3. 渲染管线

```
Tk root（overrideredirect 无边框）
 ├─ 自绘标题栏（Frame + Canvas 图标按钮）
 ├─ 侧栏（Frame + W.NavItem[Canvas]）
 └─ 主区
    ├─ 页头（Frame + Label + W.StatusPill[Canvas]）
    └─ 页面栈（4~7 个 Frame 常驻叠放，lift 切换）
       ├─ W.StatCard[Canvas]
       ├─ W.Panel[Canvas + 内嵌 Frame]
       ├─ W.Steps / W.SegBar / W.Bar[Canvas]
       └─ W.EventList[Frame + Text + SlimScroll[Canvas]]
```

绘制顺序依赖“Canvas 画底 → 普通 Frame/Label 浮在其上”。圆角通过多边形模拟，文本由 Windows 字体渲染，二者抗锯齿能力不一致，边缘观感因此割裂。

## 4. 各控件绘制方式

| 控件 | 绘制方式 | 锯齿/清晰度问题 |
| --- | --- | --- |
| `Panel` | `round_rect()` 24 点/角多边形 + 内嵌 Frame | 多边形边缘无 AA；1px 描边用“外扩填充环”模拟，仍发毛 |
| `Btn` | Canvas 圆角多边形 + `create_text` | 同上；悬停/按下靠颜色插值，无形状 AA |
| `StatCard` | Canvas 圆角 + 文字 + 2px 进度线 | 圆角与细线边缘毛刺；数字为字体渲染 |
| `Steps` | Canvas 圆点 + 线段 + 文字 | 小圆点边缘明显阶梯 |
| `SegBar` / `Bar` | Canvas 圆角条 | 细条边缘不锐利 |
| `Chip` / `Switch` / `Stepper` | Canvas 圆角 + 圆点 | 胶囊端部与开关滑块有阶梯 |
| `NavItem` | Canvas 圆角高亮块 + MDL2 图标 | 高亮块圆角发毛 |
| `StatusPill` | Canvas 胶囊 + 圆点 | 同上 |
| `EventList` / 旧 `LogTable`、`LogView` | `tk.Text` + tag 着色 + 自绘滚动条 | 文本走系统字体渲染；滚动条为 Canvas 细条 |
| `SlimScroll` | Canvas 圆角滑块 | 8px 宽滑块边缘毛刺 |
| `IconBtn` | Canvas 文字字形 | 图标即字体，尺寸/线宽不可控 |
| `ModeCard` | Canvas 圆角 + `PhotoImage` + 文字 | 位图与圆角边缘质量不一致 |

统一根因：`round_rect()` 每角 18 段折线，且 Tk 无 `QPainterPath` 级别的 AA；1px 边框在 Tk 的 `create_line/polygon` 上无法获得亚像素覆盖。

## 5. 字体与图标资源

### 字体
- 界面：`Microsoft YaHei UI`；等宽：`Consolas`；图标：`Segoe MDL2 Assets`（`theme.py`）。
- `T.f(size)` 使用**磅值**，随 `tk scaling`/系统 DPI 变化；而布局大量使用像素常量（42/46/68/220/232 等）。两者增长模型不同，高缩放下容易出现字大框小、切字。
- 文本抗锯齿由系统字体渲染提供，Tk 不暴露 hinting/亚像素控制；与自绘图形边缘的清晰度不一致。

### 图标
- 功能图标 = MDL2 私有码位（如 `\uE80F`、`\uE713`），依赖系统字体存在且版本一致。
- 品牌/入口图 = PNG：`assets/brand_24..64.png`、`app_24/44/64.png`、`mode_old.png`、`mode_dingtalk.png`。
- 仅品牌图标按 `winfo_fpixels("1i")` 选择 24/30/32/36/44/48（`ui.py` 的 `brand_px` 逻辑）；其余 PNG 以原始像素 1:1 显示，无 `@2x`/矢量版本。
- 没有 SVG 图标管线，线宽、光学尺寸无法跨控件统一。

## 6. 位图放大情况

- 代码中**没有**对 `PhotoImage` 使用 `zoom()`/`subsample()` 放大，因此不存在“低分辨率图被代码放大”的直接模糊。
- 但固定像素 PNG 在 150%/200% 缩放下物理尺寸偏小、观感偏弱；若后续为适配而 `zoom(2)`，就会变成真正的位图放大模糊。当前应视为“缺少高 DPI 资产”，而不是“已放大”。
- MDL2 字体图标随字号放大是矢量的，但字形设计与 16px 网格不匹配时，线宽会失真。

## 7. Windows DPI 感知

- `ui.py` 的 `_enable_dpi_awareness()` 调用 `SetProcessDpiAwareness(1)`，即 **System DPI Aware**，不是 `PerMonitorV2(2)`。
- 未处理 `WM_DPICHANGED`；窗口在 DPI 不同的显示器间移动时，由 Windows 做位图拉伸 → 整窗发虚。
- 初始尺寸用 `SPI_GETWORKAREA`（主屏工作区），最大化固定 `0,0`，副屏最大化不可靠。
- `_sync_window_size()` 在 300ms 后用 `GetClientRect` 反推 `geometry`，是对 DPI/边框差异的补丁，存在二次校正与闪烁风险。
- 未按显示器取工作区；未在 `tk scaling` 变化时重排。
- 结论：**DPI 感知只覆盖了“单屏、启动时”场景**，与 Windows 11 多屏高 DPI 的预期不符。

## 8. UI 与自动化业务耦合

- 依赖方向：`ui.py → client / dingtalk / newsapi / engine / config`；业务模块**没有**反向 import UI，方向基本正确。
- 但 `ui.py` 承担了业务编排：`_run_job()` 调用 `LikeEngine.ensure_http()/run()`、应用 `_apply_settings()`、用 `parse_user_date()` 校验日期；`_refresh_status()` 直接调 `client.resolve_debug_port()`。
- **统计耦合**：`_ingest()` 用正则解析引擎的人类可读日志（`板块：`、`列表里共 N 篇`、`[i/n] 状态 标题`、`时间段筛选：…`）来驱动卡片与阶段。日志文案一变，统计即静默失效。
- **配置耦合**：UI 直接修改 `Config` 字段并 `save_debug_port()`，配置格式本身未变。
- **线程不安全**：`_run_job()` 在工作线程中读取 `StringVar`/自绘控件值（`self.since_var.get()`、`self.limit_stepper.get()`），Tk 变量不是跨线程安全接口。

## 9. 线程、队列与日志机制

| 机制 | 实现 | 风险 |
| --- | --- | --- |
| 任务线程 | `threading.Thread` 内新建 asyncio loop 运行 `_run_job` | 工作线程读 Tk 变量 |
| 日志回传 | `log_queue` + 主线程 `after(80, _drain)`，单次最多 300 行 | 双日志视图重复解析/写入 |
| UI 事件 | `ui_queue`（status / finish / dt_*） | 无 run_id，迟到事件可能覆盖新状态 |
| 状态探测 | `_refresh_status` 另起线程，`_status_event` 等待 | 主线程 `_apply_status` 又调 `dingtalk.is_home_running()` |
| 文件选择 | `root.after(0, ask)` + `threading.Event` 等待 | 工作线程阻塞等待 UI，超时 600s |
| token 校验 | `_save_dt_token()` 主线程同步 `token_valid()`（网络，最长 8s） | 直接卡住事件循环 |
| 日志容量 | 旧 `LogView` >3000 行裁 800；新 `EventList` 已补同等上限 | 之前版本存在无上限风险 |

## 10. 可直接迁移 vs 需要适配

### 可直接复用（不改）
- `engine.py`：点赞、枚举、限流、重试、统计（纯 Python/asyncio，无 UI 依赖）。
- `client.py` / `dingtalk.py` / `newsapi.py` / `winproc.py`：客户端接管、token、进程与端口。
- `config.py`：默认值、`config.json` 读取、`APP_DIR`。
- `ws.py` / `cdp.py` 与 `tests/test_websocket.py`。
- `cli.py`：命令行入口，作为 GUI 故障时的独立回退。

### 需要适配
- 日志 → 结构化事件：把 `_ingest` 的文本解析收敛为 `RunEvent`/`LogRecord` 适配层（首版可保留解析，但集中到一处并加测试）。
- 运行参数：主线程生成不可变 `RunRequest` 快照，worker 不再读控件。
- 状态刷新/token 校验：改为后台任务 + 信号回主线程。
- 配置写入：保持 `save_debug_port()` 等既有函数与文件格式。

### 需要重写
- `ui.py`、`widgets.py`、`theme.py`、`motion.py`：Tk 绘制与动画模型。
- 图标资产：MDL2 码位 → SVG；PNG → SVG 或 @2x。
- 无边框窗口/拖拽/边缘缩放：改用 Qt 原生或经验证的 DWM 方案。

## 11. 结论

1. **边缘锯齿是 Tk Canvas 无 AA 的必然结果**，继续增加折线段数只能有限缓解，且会加重每帧重绘成本。
2. **高 DPI 问题来自 System-DPI-Aware + 像素/磅混用 + 无 Per-Monitor 处理**，不是单纯“换个大字体”能解决。
3. **图标体系缺少矢量来源**，MDL2 码位与固定 PNG 无法保证 100%–200% 下的一致线宽。
4. **业务层本身与 UI 解耦较好**，迁移的主要工作量在表现层与“日志文本 → 结构化状态”的适配，而不是重写自动化逻辑。
5. 以“抗锯齿 + 高 DPI + 矢量图标 + 统一控件状态”为目标，**Qt（PySide6）是更匹配的技术底座**；Tk 只能做到“Linear-inspired 的近似”。

详细迁移判断见《PySide6迁移可行性分析》，分层方案见《UI与业务层解耦方案》。
