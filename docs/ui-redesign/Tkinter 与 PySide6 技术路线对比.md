# Tkinter 与 PySide6 技术路线对比

## 1. 决策背景

当前应用不是简单表单：它已有无边框窗口、17 类自绘控件、实时日志、双版本连接流程、动画和自适应。目标又明确要求高保真 Linear 深色风格、细腻动画、统一弹窗、图标、DPI 和可靠回归。因此比较的重点不是“能否画出相似颜色”，而是**达到目标所需持续对抗框架的成本**。

本阶段不安装 PySide6，不修改依赖或打包配置。以下迁移均为获批后的方案。

## 2. 基于实际源码的能力比较

| 维度 | 保留 Tkinter | 迁移 PySide6 |
| --- | --- | --- |
| 现有资产复用 | 可复用 `theme/widgets/motion/ui` 的大部分结构 | 业务层可复用；Tk 控件和窗口代码不能直接复用 |
| 深色视觉 | 可以改色；能做出相似布局 | 可精确控制 QSS、自绘 QPainter、布局和主题 |
| 圆角/边框 | 18 段多边形仍无真正抗锯齿；无边框圆角已证明不可靠 | 抗锯齿矢量绘制、SVG、标准浮层，效果更好 |
| 动效 | 共享 16ms 时钟可用，但每帧重绘 Canvas；无通用子控件 opacity/transform | 属性动画、图形/控件能力更完整，可用更克制实现 |
| 输入与弹窗 | Entry/Text 可定制有限；模态、焦点和快捷键需继续自绘 | 标准输入、对话框、焦点代理、快捷键、验证器完整 |
| 可访问性 | Canvas 控件缺少读屏语义；当前只有 Btn 支持完整基本键盘操作 | 标准控件和 accessibleName/role 更容易补齐 |
| 日志/大列表 | 当前双 Text 双份数据；需手工模型和性能控制 | Model/View、委托和虚拟化更适合日志表 |
| DPI/多屏 | 当前为系统 DPI 感知，需手工补 Per-Monitor 和几何缩放 | Qt 高 DPI 与逻辑像素基础更完整，仍需实测 |
| 自动化测试 | 无成熟控件查询语义；当前只有截图工具 | 可用 Qt 测试接口、对象名、信号和模型测试，仍需零依赖测试适配或获批测试依赖 |
| 零第三方依赖 | 满足现有核心承诺 | 不满足；必须人工批准例外 |
| 打包 | 当前 PyInstaller 流程简单且已有 `--selftest` | 体积、启动、插件和 DLL 更复杂，需要独立打包验证 |
| 维护 | 代码已约 4800 行 UI；继续补齐控件语义会扩大自绘负担 | 初期重写成本高，之后可更多依赖成熟框架 |

## 3. 成本与收益拆解

### 3.1 保留 Tkinter

**需要做的实际工作**

1. 全面替换 dark tokens，并处理 Text/Entry/原生弹窗。
2. 重构页面和 compact，补全设置/连接窄宽布局。
3. 为 Chip、Switch、Stepper、NavItem、IconBtn、ModeCard 补键盘和焦点。
4. 优化 Canvas 局部绘制、圆角缓存、日志模型和动画降级。
5. 补 Per-Monitor DPI、跨屏最大化、边缘热区和圆角补丁。
6. 自绘统一模态/菜单/Toast，并建立截图回归。

**收益**

- 保持零第三方运行依赖和现有 PyInstaller 基本链路。
- 可复用页面缓存、动画时钟、队列、控件实现和现有截图工具。
- 每次可小步修改，短期交付路径直接。

**长期代价**

- 大量时间花在框架本身不提供的控件语义与绘制质量上。
- “看起来像 Linear”可以达到，但边缘质量、焦点、弹窗、动效和自动化测试难以达到同等水平。
- 自绘控件越多，后续每个页面都要承担兼容性成本。

### 3.2 迁移 PySide6

**需要做的实际工作**

1. 建立 PySide6 技术验证壳：深色、SVG、输入、日志、动画、DPI、无边框/原生外壳各做一个最小验证。
2. 提取 RunRequest、RunEvent、LogModel 和控制器；业务文件算法不变。
3. 新写 Qt 组件和 5 个界面状态；按页面与旧版对照。
4. 使用 Qt 对象名和信号建立 UI 自动化，保留截图基线。
5. 新建实验打包配置，收集 Qt 插件/DLL，验证干净机器启动、配置路径、图标和 `--selftest`。
6. 评估 PySide6/Qt 的 LGPL 或商业许可及内部分发义务，记录许可证和第三方声明。

**收益**

- 更容易实现低饱和深色、抗锯齿、统一组件、标准键盘/焦点和可控动画。
- Model/View 和信号槽更适合结构化事件、日志和可测试 ViewModel。
- 避免继续扩大 Tk 自绘框架，长期 UI 演进成本更低。

**长期代价/风险**

- 破坏当前“零第三方依赖”卖点，安装、构建和发布流程需要版本化。
- Tk UI 代码无法直接迁移，需重写表现层并做功能平等验收。
- 包体、启动行为和杀毒软件表现可能变化；不能在未测试时承诺单文件体验不变。
- 许可、Qt 插件和高 DPI 不是“导入库就自动完成”。

## 4. 量化决策表

评分 1–5，5 为更优；权重体现本次“现代化专业 Linear 工作台”的目标，而非通用项目结论。

| 维度 | 权重 | Tkinter | PySide6 |
| --- | ---: | ---: | ---: |
| 视觉保真与绘制质量 | 25% | 2 | 5 |
| 动效与交互反馈 | 15% | 2 | 5 |
| DPI、多屏、窗口可靠性 | 15% | 2 | 5 |
| 键盘与可访问性 | 10% | 1 | 4 |
| 自动化与长期测试 | 10% | 1 | 4 |
| 现有 UI 代码复用 | 10% | 5 | 2 |
| 零依赖与打包简洁 | 10% | 5 | 2 |
| 长期维护 | 5% | 2 | 4 |
| **加权结果（满分 5）** | **100%** | **2.40** | **4.15** |

该评分只辅助决策；真正的硬门槛是“零第三方依赖是否不可改变”。

## 5. 明确建议

### 推荐：PySide6 渐进式替换表现层

理由：本次目标与 Tk 当前短板的重叠度过高。继续在 Tk 上补抗锯齿、多 DPI、弹窗、键盘和测试，会把 UI 重构变成维护一个自研 GUI 框架。PySide6 的初期迁移成本更高，但更匹配最终质量与长期维护。

**必须保留不动或等价迁移的业务能力**：

- `engine.py`：点赞、枚举、重试、限速、统计等核心逻辑。
- `client.py` / `dingtalk.py` / `newsapi.py`：客户端和凭证能力。
- `config.py`：默认配置、外部文件位置和兼容格式。
- `cli.py`：命令行入口必须保持可用，成为 GUI 故障时的独立回退。
- WebSocket/CDP 实现及现有测试。

### 迁移方式：并行新壳，不做大爆炸切换

```text
旧 app.py → tbeplus.ui（保持可运行）
                 │
                 ├─ 共享 RunRequest / RunEvent / Controllers
                 │
实验入口 → PySide6 Shell → 逐页达到功能平等
                 │
       全部验收后，人工批准修改正式入口和打包
```

不建议在同一个顶层窗口混嵌 Tk 与 Qt，也不建议在一次提交里同时换 UI、改引擎和改打包。

### 条件性降级：坚持零依赖则保留 Tkinter

如果人工确认零依赖优先级高于视觉/可维护性，则采用 Tkinter，并明确验收措辞为“Linear 风格启发”，接受：

- 圆角/窗口边框不保证与 Qt 同等平滑；
- 键盘和读屏只覆盖约定范围；
- 动效以短颜色过渡为主；
- 自动化以状态单测 + 截图对比为主；
- 不再投入高成本模拟 Qt 的全部能力。

## 6. 决策门与退出条件

在正式选择前，仅经人工批准后做一个隔离技术验证，验收以下问题：

1. 深色主题和 SVG 在 100/150/200% 下是否清晰。
2. 按钮、输入、开关、菜单、模态、日志表是否满足组件规范。
3. 原生或自绘窗口在最小化、最大化、跨屏时是否稳定。
4. 10 万条模拟日志的模型/筛选策略是否满足有界内存和响应要求（不代表真实点赞压测）。
5. fake engine 是否能完整跑通准备、试运行、停止、成功和失败。
6. 实验包能否在干净 Windows 启动并找到配置和资源。
7. 依赖与许可是否获项目所有者接受。

若 PySide6 验证未通过或依赖不被批准，回到 Tkinter 降级路线；不通过继续堆临时补丁来掩盖决策。
