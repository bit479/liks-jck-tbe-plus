# liks jck tbe+

**新闻点赞 1.8.3 版本** —— 一个自动给 TBe+ 新闻资讯点赞的小工具。

把所选版本里每一篇还没点赞的文章都点上；已经点过的会自动跳过，不会重复点。

包装成了一个双击就能跑的小程序（图形界面），不用记命令，**也不用装任何第三方库**。

打开软件先选版本，两套板块**分开跑、互不干扰**。钉钉版从 1.8 起
**只认新版 TBeHome.exe**，不会启动、也不会读取旧版 TBe+ 客户端：

| 版本 | 板块 | 说明 |
| --- | --- | --- |
| **老版本 TBe+** | 新闻资讯 / 开讲了 / 进出口公司新闻资讯 | 传统桌面客户端，需要重启并接管客户端 |
| **钉钉版 TBe+** | 钉钉版e+新闻资讯 | 新版钉钉套壳的「新闻资讯」，各公司订阅号全部资讯 |

界面是 1.6 重做的：无边框沉浸式标题栏（和左侧深色导航连成一片）、白色卡片工作区，
分「概览 / 运行日志 / 任务设置」三页。跑起来能看到每个板块的进度、当前正在处理哪篇、
以及新点赞 / 原本已赞 / 未成功的实时计数；日志按「时间 + 级别 + 消息」三列排，
可以按「全部 / 关键 / 问题」过滤、暂停滚动、复制。（截图见 `docs/screenshots/`）

1.8 把主界面改成了「TBE+ 自动化中心」仪表盘：面包屑 + 任务概览、
已处理/新点赞/原本已赞/未成功四张指标卡、执行控制台（三步流程 + 当前资讯）、
处理进度分布、运行质量、可搜索的实时日志表；新增「账号与连接」页，
钉钉版首次进入会自动启动新版客户端并接管 token，失败时给出三步引导。
1.7 加了一套克制的动效：页面切换轻位移、统计卡首屏交错淡入、按钮/开关/导航
平滑变色、进度条平滑推进、日志新行轻淡入（高频时自动降级）。
系统「关闭动画效果」或设 `TBE_REDUCED_MOTION=1` 时全部动效即时完成，
任务与数据更新不受影响。

1.8.1 修了两处实际使用中的毛病：左上角原来标题栏和侧边栏各画了一遍
图标 + 「TBE+ 自动化中心」，看着像重影，现在只保留一处，标题栏也改成
左深右浅的分色（和设计稿一致）；运行时（尤其钉钉版）原来会不断闪出
黑色命令窗口，现在进程 / 端口 / 快捷方式 / 卸载项查询全部改用纯 Win32
（`tbeplus/winproc.py`），不再启动任何 PowerShell / tasklist 子进程。

1.8.2 换了「眨眼宝宝点赞」品牌图标（多尺寸、按 DPI 选），统一圆角 Token
（窗口 14 / 卡片 16 / 控件 10 / 胶囊 999），圆弧从 6 段加密到 18 段；
切页改为"先就位再隐藏"、动画 220ms→110ms（纯切换实测约 17.7ms/次）；
最小化改成系统 `SW_MINIMIZE`、不再来回切 `overrideredirect`，并去掉启动
整窗 `-alpha` 淡入——白闪与还原跳变消失。Tk 的 Canvas 没有抗锯齿、
无边框窗口也拿不到 DWM 系统圆角，所以窗口四角仍是直角，这是技术栈限制。

1.8.3 把 4 个页面常驻叠放、切换只 `lift()`（原来每次切页都重新 `place`，
首页重排要 190ms，看着像卡白屏；现在双向约 11–19ms）；修了「运行质量」
卡片底部标签被圆角裁掉；卡片/按钮的 1px 边框改成"填充环"叠法，
圆角边缘更干净（Tk 无抗锯齿仍是硬限制）。

## 快速开始

1. 装好 Python 3.10 以上版本（安装时**记得勾选 "Add Python to PATH"**）
2. 双击 **`启动.bat`**
3. 在「概览」页依次点三个按钮：

   | 按钮 | 作用 |
   | --- | --- |
   | **准备并接管客户端** | 关闭并带调试端口重启 TBe+ 客户端（登录态保留） |
   | **试运行（只看不点）** | 只扫描，列出哪些文章没点赞，**不点** |
   | **开始点赞** | 正式执行；跑的时候这个位置变成进度条和当前文章 |

「**任务设置**」页里可以设置 **新闻时间段**：

- 填「从 ___ 到 ___」两个日期，只处理这个区间内的新闻
- 勾上「**至今**」，结束日期就用今天
- 或者点「近 7 天 / 近 30 天 / 近 90 天 / 近 1 年」一键设置
- 开始日期留空 = 不限起始时间；日期格式是 `YYYY-MM-DD`

**什么都不用先装。** 电脑上没有 Python 也没关系——`启动.bat` 会用仓库里
自带的官方安装包（`installer\python-3.13.16-amd64.exe`）**自动静默安装**，
只装给当前用户、不需要管理员权限，装完直接启动程序。

整个项目也**不需要任何第三方库**：不用 pip、不用联网、不会再有依赖问题。
（详见下面「为什么零依赖」）

> **为什么要点「准备并接管客户端」？**
> TBe+ 没有网页版登录入口，新闻站还有 WAF 只放行客户端内部的请求，
> 所以只能"接管"桌面客户端。这一步会给客户端加上调试端口并重启它，
> 之后程序就能像操作浏览器一样操作它——**不需要账号密码，也不用过验证码**。
> 代价是会中断当前打开的对话窗口（登录态保留）。

## 命令行用法

不想用界面就双击 `命令行.bat`，或者直接跑：

```bash
python cli.py --check          # 看看客户端接管了没
python cli.py --attach         # 重启并接管客户端
python cli.py --list           # 只列板块和篇数
python cli.py --dry-run        # 试运行，只看不点
python cli.py                  # 正式点赞四个板块
python cli.py --only 开讲了     # 只跑一个板块
python cli.py --max 5          # 每个板块最多处理 5 篇
python cli.py --no-session     # 跳过【进出口公司新闻资讯】
python cli.py --since 2026-09-01                     # 只处理 9 月 1 日之后的
python cli.py --since 2026-09-01 --until 2026-09-30  # 只处理 9 月这一个月
python cli.py --last-days 7                          # 只处理最近 7 天
python cli.py --restart-every 60                     # 每 60 篇重启一次客户端（默认 60，0=不重启）
```

时间段也可以写进 `config.json` 的 `filter_since` / `filter_until`，
界面上改了会覆盖它。

## 速度

三个板块、2026-07-01 至今共 **250 篇**，实测全程 **约 3 分钟**打完，零失败。

| 版本 | 每篇耗时 | 250 篇实测 |
| --- | --- | --- |
| 最初版本 | 15~20s（偶尔 30s 超时） | 1 小时以上，还会失败 |
| 上一版（打开文章页面） | 3~8s | 15~30 分钟，越跑越慢 |
| **当前版（接口 + 按页枚举）** | **约 0.7s** | **枚举 10 秒 + 点赞约 2.5 分钟** |

现在的限制不再是程序，而是**新闻站自己的服务端配额**（见下）。

提速来自四处：

1. **改走接口，压根不打开文章页面**。登录之后新闻站的这三个接口直接能用：

   | 接口 | 作用 |
   | --- | --- |
   | `GET /api/article/detail?id=` | 读状态，返回 `is_digg` / `digg_count` |
   | `POST /api/article/addDigg` | 点赞 |
   | `POST /api/article/cancelDigg` | 取消赞 |

   文章的**数字 id 从列表页 Vuex store 里的 `url` 就能取到**，所以整条链路
   不需要再开文章窗口、不需要点击。

2. **每篇只发一个请求**。接口模式原先要发三次：
   先 `detail` 读状态、再 `addDigg` 点赞、最后再 `detail` 复查。
   实测下来：

   | 接口 | 实测耗时 | 说明 |
   | --- | --- | --- |
   | `GET /article/detail` | 0.7~8.1s（平均 **2.5s**） | 三个里最慢的一个 |
   | `POST /article/addDigg` | 0.57~2.0s（多数 **0.6s**） | 快 |

   而且 `addDigg` 对**已经点过赞**的文章再点一次，照样返回
   `{"code":1,"msg":"操作成功"}`，**不报错也不重复计数**
   （实测 8 篇各点两次，7 篇计数一模一样，`is_digg` 一直是 `true`）。
   所以默认不再查状态，直接点赞：**每篇 1 个请求**，比原来快 3 倍多，
   也不会再被慢查询拖到超时。

   **默认会先查一次状态**，这样才能说清"新点赞了几篇、本来就有多少"。
   不想查、只想尽快把赞点上（并且不介意统计口径）就用 `--fast`。
   想点赞后再确认一次就用 `--verify`。

3. **列表直接问新闻站要，不再滚动、也不再受门户那张卡片的 200 篇限制**
   （见下面的"200 篇之谜"）。

4. **列表拿到起始日期就停**。设了"从某天开始"就不用把整条频道拉完。

接口模式用不上时会退回"打开文章页面"的老办法，那条路上也有两处优化：
点击改成页面内派发事件（20 毫秒，原先是 5 秒）、点赞校验改成 0.3 秒轮询。

### 统计口径：为什么以前全是"新点赞"

1.1 版及以前默认**不查历史状态**：每篇都直接发一个点赞请求，接口返回 `code=1`
就记成"新点赞"。于是"本来早就赞过"的文章也全被算进"新点赞"，
汇总里必然出现"原本已点赞 0 篇"——数字看着就像新点了几百篇，其实是假的。

现在默认**先查一次状态**（`api_read_state = true`），口径分成三档：

| 显示 | 含义 |
| --- | --- |
| 新点赞 N | 查过状态、确认原来是没赞的，这次点上了 |
| 原本已点赞 N | 查过状态、本来就是赞着的，**不需要再点** |
| 已确认点赞 N | 只发了点赞请求（快速模式或状态读不到），服务端已受理，但分不清是否本来已赞 |

另外还有两类会单独列出来、不会被藏起来：
**点赞已受理待复查**（点赞返回成功，但复查没看到状态变化）和
**未成功**（并附上原因，比如"读状态失败 5""登录超时 1"）。

汇总也重新排版了：先给"全部板块合计"，再用横线分隔各板块明细，
避免把某个板块的小结误当成总数（之前就出现过"小结 36 / 合计 396"这种困惑）。

两种模式的代价：每篇都是 1 个请求（一个查状态 / 一个点赞），
所以**重复跑一次速度几乎一样**；只有"第一次跑、确实有一大批要新点"时，
查状态模式会多出一倍请求（查完再点）。要跳过查状态就用 `--fast`。

### 服务端配额：为什么一口气点太多会整片失败

新闻站对点赞接口有配额，实测**大约每 60 秒只放行 120 次**：

- 跑到第 121 次请求开始，返回的业务码不再是成功，**整片整片地失败**；
- 这时候立刻重试没用（撞在同一个时间窗里），
  这正是以前"总是提示重试仍失败"的真实原因；
- 停一会儿再试就恢复了。

所以程序会**限速**：默认 `api_rate = 1.4`（约 84 次/分钟），
给翻页请求留出余量；一旦哪一批出现失败，还会自动再降速，
并按 20 秒 / 40 秒 / 80 秒逐轮退避重试，跑完全部都能成功。

代价是速度被服务端卡在**每秒 1~2 篇**——这已经是上限，
再快换来的就是整片失败重来。

> 如果接口模式因为客户端版本差异用不了，程序会自动退回"逐个打开文章页面"
> 的老办法，功能不受影响（只是慢一些）。用 `--no-api` 也能强制走老办法。

### 为什么会"越跑越失败"

客户端每打开一篇文章就会新建一个 `<webview>` 页面、**而且从不回收**。
我实测跑 20 篇就堆了 20 个，这些都是活着的渲染进程，持续占用 CPU 和内存。
堆多了之后文章渲染越来越慢，最后超时——表现就是"重试仍失败"。

程序现在**每处理 60 篇就重启一次客户端**把它清零，然后重新打开频道接着往下做
（已经处理过的会自动跳过）。重启一次约 1 分钟，用 `--restart-every` 可以调
（0 = 不重启）。

> 我试过直接删掉那些残留的 `<webview>` 元素，数字上很有效（20 个 → 1 个），
> 但会**破坏客户端窗口的内部记账**，之后列表页一打开就被顶掉。所以只能用重启，
> 不能动它的 DOM。

## 它到底是怎么做到的

### 为什么不用 Playwright

一开始用 Playwright，但 TBe+ 桌面端是 2023 年版本的老 Electron 内核，
`connect_over_cdp` 一连上就报：

```
Protocol error (Browser.setDownloadBehavior): Browser context management is not supported
```

所以改成了自己写一个极简的 CDP 客户端（`tbeplus/cdp.py`，200 行不到），
只用 `Runtime` / `Input` / `Page` 这几个最基础的域——老内核全都支持。

### 为什么零依赖

CDP 需要一条 WebSocket 连接。一开始用了第三方库 `websockets`，
结果用户那边 `启动.bat` 经常卡在
`[错误] 依赖安装失败，请检查网络后重试`——因为 Windows 上
`where python` 很容易命中**微软商店的占位符**，那个东西根本没装 Python，
后面 `import websockets`、`pip install` 自然全失败。

所以干脆用标准库自己实现了 WebSocket 客户端（`tbeplus/ws.py`，
握手 / 掩码 / 分片 / ping-pong / 关闭帧都覆盖了），
**从此一个第三方包都不需要**：不用 pip、不用联网、不会再有依赖问题。

这套实现有自带的自检：

```bash
python tests/test_websocket.py
# [PASS] WebSocket 实现全部通过（握手 / 掩码 / 大消息 / 分片 / ping-pong / 事件）
```

### 实测出来的页面结构

```
门户页 miniapp://portal/#/
└── 卡片 .card-title = "新闻资讯" / "开讲了"
    └── 卡片里的 .card-header-button（"更多"）
        └── 频道文章列表页  https://<内容站>/pubacc-front/article/list?contentSource=[...]
            └── 文章条目 .article-item > .article-title
                └── 点标题 → 文章窗口里开一个新标签页
                     https://<新闻站>/pc/show?id=...&f=...&yzj_id=...
                     └── 点赞按钮  ★关键★
                           未点赞  <span class="praise-num">10476</span>
                           已点赞  <span class="praise-active">10477</span>
```

几个踩过的坑，都写在代码注释里了：

- **列表页本身没有点赞按钮**，点赞在文章详情页里，所以必须逐篇打开。
- **列表页是无限滚动的**：一屏只有 10 篇，得一直往下滚才会继续加载。
  实测【新闻资讯】有 **200 篇**，只读首屏会漏掉 95%。
- **文章页需要一个 token**，而只有 **门户卡片** 生成的链接带 SSO 票据；
  列表页点出来的链接不带。不处理就会一直报
  "文章获取错误：登录超时，请重新登录"。
- **文章是开在同一个窗口的多个标签页里的**，关闭时要关标签（`em.tab-close`），
  关掉全部标签会让窗口消失。
- **`Target.closeTarget` 和 `window.close()` 都关不掉这个窗口**。
- **会话型板块里的文章卡片点不开**（`<a>` 高度甚至是 0），
  换成读取消息组件数据里自带的文章 URL，再直接导航过去。
- **点赞后状态刷新有延迟**，判"没点上"之后再等一轮确认。

### 登录预热（解决"登录超时"）

文章详情页会先看 URL 里有没有 `ticket`，没有就尝试静默登录，两者都没有就报
「登录超时」。而只有**门户卡片**里的文章链接会带 `ticket=APPURLWITHTICKET…`。

所以程序每次开跑前会先做一次**登录预热**：

1. 在门户页点开第一篇文章（这个链接带票据）
2. 等它把点赞区域渲染出来，说明登录态已经建立
   （token 会写进 `tbeanews` 域的 cookie `tbea_art_token`）
3. 关掉这个标签页，再开始正式遍历

登录一次之后，后面所有直连的文章地址（包括消息里那些不带票据的 URL）
就都正常了。如果中途登录态掉了，程序会自动再预热一次并重试当前文章。

### 列表按页拉取（解决"漏识别"）

早期版本靠"滚动加载"把频道里的文章翻出来，同一份列表**两次跑出来的篇数居然不一样**
（一次 200 篇、一次 180 篇，缺的还不是同一批）——这就是"漏识别"。

把列表页自己的加载函数挖出来看，原因很清楚：

```js
_getArticleList() {                      // 页面自己的"加载下一页"
  if (!this.isLoading && !this.isEnd &&
      document.scrollingElement.scrollTop + window.innerHeight + this.scrollThreshold
        >= document.scrollingElement.scrollHeight) {      // ① 必须"文档滚动条到底"才算数
    this.isLoading = true;
    this.getArticle({ ... pageIndex: this.cardArticleList[this.currentTabIndex].pageIndex })
      .then((e) => { this.isLoading = false; if (e === 0) this.isEnd = true; });   // ② 翻页号是响应回来才自增
  }
}
```

1. 它只认 `document.scrollingElement` 滚到底——滚里面那个列表容器根本没用；
2. `pageIndex` 是**异步响应回来才自增**的。原来的代码为了治"列表卡死"，
   会硬把 `isLoading` 改回 `false` 再调一次，于是**同一个 `pageIndex` 发出去两个请求**，
   两个响应各把页码加一次，**中间那一页 10 篇就永远跳过了**。

现在改成**直接调 store 的 action，自己指定页码一页页拉**：不依赖滚动、不依赖 `isLoading`。

还踩过一个坑：列表页渲染出第一屏之后会偷懒，**大约 5 秒后才自己去加载下一页**。
实测开讲了 15 篇，第 0~4.5 秒一直只有 10 篇、`isLoading` 还是 false，
第 5 秒才开始加载、5.5 秒才变成 15 篇——这时候要是已经判定"到底了"收工，
就会整整漏掉一页。所以现在要连续两次"接口说没有了、而且列表真的几秒没动静"
才收工，中间只要又长出东西就接着往下拉。

### "200 篇之谜"：门户卡片接口只给 200 篇

按页拉取修好之后，新闻资讯**稳定**是 200 篇 —— 但用户说"不止 200 条"。
查下来是**接口本身的限制**，不是我们漏了：

- 门户那张卡片用的 `card/getArticleList`，**放大 pageSize（100、200 都试了）、
  翻到 21 页以上，全都是"没有了"**，最多就给 200 篇（第 21 页明确返回 0）；
- 而**新闻站自己**的接口没有这个限制：

  ```
  GET /api/article/lists?section_code=news&page_no=1&page_size=100
  ```

  实测 `section_code=news` 的 `count` 是 **3286** —— 新闻资讯一共有三千多篇，
  门户那张卡片只给最近 200 篇。`page_size` 给 500 也照收。

所以现在改成**直接问新闻站要列表**。`section_code` 从 `/api/pc/portal` 的
栏目名反查（新闻资讯=news、开讲了=lecture、要闻=headline），
文章按时间从新到旧排，翻过起始日期就停。

实测（时段 2026-07-01 至今）：

| 板块 | 旧（门户卡片） | 新（新闻站接口） |
| --- | --- | --- |
| 新闻资讯 | 200 篇（最早只到 08-10） | **341 篇（一直翻到 07-01）** |
| 开讲了 | 15 篇 | 15 篇（栏目共 125 篇） |
| 进出口公司新闻资讯 | 36 篇（读消息里的 URL） | 36 篇（会话型，不变） |

拿不到栏目接口时会自动退回原来的门户卡片方式，功能不受影响。

### 钉钉版 e+ 新闻资讯（新版 TBe+）

新版 TBe+ 换成了**钉钉 8.5 套壳**（`DingtalkLauncher.exe` → `TBeHome.exe`，
Chromium 133 内嵌内核）。它左边有一个「新闻资讯」栏，右上角有「我的未读新闻」，
文章页是：

```
https://tbeanews.tbea.com/pc/news?id=15857
```

（旧版是 `/pc/show?id=`，新版是 `/pc/news?id=`。）

实测这个栏目就是新闻站的**「全部资讯」**：各公司/部门订阅号（新闻资讯、开讲了、
廉洁风控直通车、各子公司新闻资讯……）的汇总，共 **1.4 万+ 篇**，接口是：

```
GET /api/article/lists?page_no=1&page_size=200      # 不带 section_code
```

点赞仍然是同一个 `POST /api/article/addDigg`，所以不用去点钉钉的界面
（钉钉这个版本把 `--remote-debugging-port` 屏蔽了，界面自动化也接不上）。

用法和别的板块一样，`--only 钉钉版e+新闻资讯` 可以单独跑：

```powershell
python cli.py --only 钉钉版e+新闻资讯 --since 2026-10-01
python cli.py --list          # 会显示"共 14881 篇（最新 ...）"
```

> 这个板块有一万多篇，**建议一定设起始日期**。没设的话程序默认只跑最近
> `dingtalk_default_days`（默认 7）天，并在日志里说明，免得一跑几个小时。
> 界面里也有「跳过【钉钉版e+新闻资讯】」的勾选框。

## 免客户端运行（纯 HTTP 模式）

新闻站只认一个 Cookie：

```
Cookie: tbea_art_token=<32 位十六进制>
```

带上它就能直接调 列表 / 详情 / 点赞 三个接口，**不需要旧客户端、也不需要钉钉客户端在线**
（已实测：把旧客户端全部关掉，列表、读状态、点赞、统计都正常）。

程序按这个顺序找 token：

1. `config.json` 里的 `news_token`（也可以用 `python cli.py --token <token>` 写入）；
2. `state.json` 里上次验证通过、自动缓存的 token；
3. 从已登录的客户端进程内存里读（新版 `TBeHome.exe` 优先，其次旧版 `TBe.exe`）。

所以日常用的时候：

```
打开新版 TBe+ → 左边"新闻资讯"随便点开一篇（让它拿到 token）
→ 运行本程序：它会自动取 token、存进 state.json，之后就不用客户端了
```

token 失效时（一般会过一段时间）重新做一次上面的动作，或者手动：

```powershell
python cli.py --token 51bc7dc5a39d4a93aef3e8d4f238a99f
python cli.py --check          # 显示"纯 HTTP 模式（不需要客户端在线）"
```

> 注意：
> * `state.json` 里是登录凭证，已被 `.gitignore` 排除，**不要发给别人**；
> * 【进出口公司新闻资讯】是会话里的消息，仍然需要旧客户端读消息列表；
>   纯 HTTP 模式下会明确提示跳过这个板块，其它板块不受影响；
> * 想强制回到旧的客户端方式：`--no-http`。

### 时间段是怎么判断的

列表页每条文章的缩略图地址里就带着发布日期：

```
https://ejia.tbea.com/pubacc/public/data/26/09/30/WXcdBIzk.jpg?...
                                        └──┬──┘
                                     2026-09-30
```

程序从这段路径里取 `年月日`；取不到时退回用列表里显示的日期文案
（`09/30` 这种只有月日的，按今天推算年份，比今天晚一个月以上就算去年）。
会话型板块的文章用所在消息的发送时间。

筛选是在**打开文章之前**做的，所以不在范围内的文章根本不会被点开，很快。
少数实在认不出日期的文章会照常处理（宁可多点赞，也不要漏），并在日志里
告诉你有多少篇属于这种情况。

### 【进出口公司新闻资讯】的特殊处理

这个板块不在门户卡片里，而是左侧消息列表里的订阅号会话。
它的文章卡片用合成事件点不开，但消息背后的 Vue 组件
（`name: NewsItem`）的 `$props.msg.param.list` 里**直接带着每篇文章的完整地址**：

```json
{
  "title": "坦桑尼亚能源部部长视察特变电工东北电网一期Morogoro 220千伏变电项目",
  "url": "https://<新闻站>/pc/show?id=13987&f=HLvsJiPj&yzj_id=0d41f4fe-..."
}
```

所以流程是：滚动会话加载历史 → 抽出所有 `{title, url}` → 用客户端里一个
现成的 webview 挨个导航过去 → 读状态、按需点赞。比点卡片稳得多，也不会开一堆窗口。

## 配置

所有可调项都在 `tbeplus/config.py` 的 `DEFAULTS` 里。
想改的话，把 `config.example.json` 复制成 `config.json` 再改，
**`config.json` 不会被提交到 git**，方便各自放自己环境的东西。

常用的几项：

| 配置 | 说明 |
| --- | --- |
| `debug_port` | 调试端口，默认 9222 |
| `client_exe_candidates` | TBe.exe 可能的位置，找到哪个用哪个 |
| `portal_cards` | 门户首页上的新闻卡片名 |
| `session_channel` | 会话型板块名 |
| `skip_session_by_default` | 是否默认跳过会话型板块 |
| `praise_selector` | 未点赞按钮的选择器 |
| `praise_active_selector` | 已点赞按钮的选择器 |
| `wait_after_click` / `confirm_wait` | 点赞后的等待时间 |

## 常见问题

**双击 `启动.bat` 提示"没能准备好 Python"**

正常情况下程序会自动装好 Python，出现这个提示说明自动安装也没成功，
常见原因两种：

1. 复制/下载的时候漏了 `installer` 目录，或者安装包不完整；
2. 安装被公司的系统策略或杀毒软件拦了。

可以先手动装一次（[python.org](https://www.python.org/downloads/)，
记得勾选 **Add python.exe to PATH**），装完再双击 `启动.bat`。

> 老版本会报 `依赖安装失败，请检查网络后重试`——那是把"找不到 Python"
> 误报成了网络问题，现已修好。

**提示"文章页显示登录超时"**

程序现在会**自动登录预热**，正常情况下不会再有这个提示了（见上面
「登录预热」那一节）。

如果还是出现，说明自动预热也没成功——请先在 TBe+ 客户端里手动点开
一篇新闻，确认能正常显示；如果客户端自己也打不开，在客户端里重新
登录一次，然后重跑本程序。

**提示"没检测到 TBe+ 在运行"**
先把 TBe+ 客户端打开，再点「① 准备」。

**提示"没能找到 TBe.exe"**

程序会按下面顺序自动找，一般不需要你操心：

1. 正在运行的 TBe 进程（直接拿它现在的路径，最准）
2. 桌面 / 开始菜单里的 TBe+ 快捷方式
3. 卸载注册表项里的安装目录
4. App Paths 注册表项
5. `Program Files`、其他盘符等常见位置通配搜索

同一个 `tbea` 目录下通常有两个 `TBe.exe`：一个是几百 KB 的小启动器，
真正的主程序在带版本号的子目录里（体积上百 MB）。程序会自动挑主程序。

如果五条路都没找到，**界面会弹出一个文件选择框让你手动指定**，
选一次就记进 `config.json`，以后不用再选。

命令行下也可以直接指定：

```bash
python cli.py --client-exe "D:\...\tbea\2305251534\TBe.exe"
```

**点「① 准备」之后一直等不到端口**

程序现在会**自动换端口**（见下面「端口冲突」那一节），所以先看日志里
有没有"自动改用端口 xxxx"的字样。如果还是起不来，通常是这几种：

1. **TBe+ 自己没退干净**。它是单实例的，旧进程还在的话，新进程只会把
   窗口唤到前面然后自己退出，调试端口根本不会开。
   日志里会有提示，手动退出 TBe+（托盘图标右键退出）再点一次即可。
2. **选到的 `TBe.exe` 是启动器而不是主程序**。几百 KB 的那个是启动器，
   命令行参数可能传不到主程序；在弹窗里选带版本号子目录里那个大的。
3. **被安全软件拦了**，这种情况日志里通常能看到客户端进程直接消失。

### 端口冲突（"9222 连不上 / 端口报错"）

程序**不写死 9222**，它会：

1. 先用 `config.json` 里配的端口（默认 9222）；
2. 如果这个端口被别的程序占着，或者**落在 Windows 的保留端口段里**，
   就自动往后找一个真正能用的端口（9223、9224…）；
3. 把实际用的端口写回 `config.json`，以后就一直用它。

日志里会写清楚换成了哪个端口，以及原端口被谁占用：

```
端口 9222 当前不可用（被 chrome (PID 12345) 占用）
  自动改用端口 9223
调试端口已就绪
```

> **为什么会落在保留段里？**
> 装了 Hyper-V / WSL / Docker 之后，Windows 会预留一些 TCP 端口段，
> 落在里面的端口**连管理员也绑不上**。可以这样查看：
>
> ```powershell
> netsh int ipv4 show excludedportrange protocol=tcp
> ```
>
> 程序用「实际绑定一下试试」的方式判断，所以这种保留段也能自动躲开。

也可以直接改 `config.json` 里的 `debug_port` 换一个起始端口，比如 `19222`。

**某个板块打不开 / 篇数是 0**
多半是版面改过了。用 `python cli.py --list` 看看，再对照
`config.example.json` 里的选择器调整。

**点了半天没反应**
确认 TBe+ 客户端是"接管后"启动的（界面上状态应该显示
`● 已接管`）。普通启动的客户端没有调试接口。

**会不会把已经点过的又点一遍？**
不会。程序先读状态，`praise-active` 的会直接跳过。重复运行是安全的。
